# Build notes

Decisions and shortfalls recorded while building Tie-Out.

## Foundations

- `Results` holds `meta`, `assumptions`, `totals`, `trace` and `scorecard` as plain JSON in `results.json`; frames are Parquet. `scorecard` is `None` or a dictionary.
- `Results.empty()` uses zero-column data frames; real column sets arrive with the modules that fill them.
- `DEFAULTS` in `tieout/assumptions.py` is a nested dictionary. Probability triples are `{"low", "base", "high"}` mappings; reference bands are `{"low", "high"}` mappings holding fractions (0.01 means 1%).
- Capture probabilities, discounts, caps, ramp values and other shares are validated to lie in [0, 1]; reference bands need 0 <= low <= high. Days, months and dollar defaults are not range-checked.
- `merge_overrides` deep-merges user overrides over the defaults and does not validate; callers run `validate` on the merged result.
- The CLI returns exit code 2 when an input file is missing or unreadable, or when validation blocks (the PRD's blocking-error code; see "Pipeline and CLI"), and 0 otherwise.

## Vendor matching

- **V0 punctuation.** Apostrophes and periods are deleted ("O'Brien" -> "obrien", "S.A." -> "sa"); all other punctuation becomes a space ("Coca-Cola" -> "coca cola"). A dangling "and" left by legal-form removal ("Smith & Co" -> "smith") is dropped, and at least one token is always kept ("Ltd" stays "ltd").
- **V0 branch markers.** The `(plant|site|branch|store|dc|whse) <alphanumerics>` form is taken when it is in parentheses, or when the trailing token contains a digit or is a single letter ("Store #12", "Plant A"). Without that restriction "Acme Site Services" would lose "site services" and exact-match plain "Acme". The trailing `- <words>` form needs whitespace before the dash so hyphenated names are kept. Markers are peeled repeatedly ("Acme Corp - Chicago Plant 3" -> branch "chicago plant 3"). A dba alias's branch is used when the primary part has none.
- **V2 uses aliases, V4 does not.** Exact-name grouping uses the primary name and every dba alias. V4 scores distinct primary names only.
- **Rare token for small inputs.** "Fewer than 1% of distinct names" can never hold for a shared token when there are fewer than 200 names, so a token counts as rare when it appears in fewer than `max(1% of distinct names, 3)` names. That means a token shared by exactly two names always blocks. Prefix blocking uses `name[:4]` of the normalised name.
- **Guards.** The score is computed on the name with generic tokens removed. If nothing is left, the full normalised name is scored instead, and the weak-name cap (91) applies. The descriptor clash cap (74) takes precedence over the 91 caps. The `cdist` pre-filter uses the unguarded score with a 0.05 tolerance, and survivors are re-scored exactly by one scalar function, so fresh and cached runs see identical scores.
- **V2 split groups.** In a split group, each `(country, tax ID)` set of records is one unit, and every record with no comparable tax ID is a unit of its own. Representative pairs (smallest key per unit) between units go to review: as `vendor_sibling` when the two are tax-vetoed, otherwise as `vendor_match` at tier C. This also covers no-tax records reviewed against each other and same-name records from a different country. Taking "not merged automatically" literally, records with no tax ID in such a group are not merged even with each other.
- **V5 "every distinct name" test across two clusters.** When two multi-record clusters meet, every tested name on one side must score >= `review_threshold` against every tested name on the other side, and each record's own name counts as tested. Tested names come from V2 merges (only where the shared name is a record's primary name) and from both ends of a V4 merge. Names attached by tax ID, by dba alias or by a reviewer's approval are not tested. The test re-scores those few name pairs on the fly, including on the `cached_pairs` path.
- **Exact names are left to V2.** A record pair that already has a V1 or V2 row is never re-decided by V4, even when the V2 outcome was "review". Fuzzy similarity therefore cannot override a split decided on exact-name evidence.
- **Decisions.** Approved `vendor_match` pairs are applied after V1 and before V2 as forced merges. The reviewer overrides a tax-ID veto. Rejected `vendor_match` pairs act as cluster-level cannot-links for V2 and V4 (but not V1), so neither record can be pulled together with the other through a third record. A deferral counts as "no decision" for clustering and shows as `deferred` on a pair that would otherwise be pending. Approved siblings, together with any parent-table links, are grouped. The group's `parent_id` is the smallest `P:` parent in it, otherwise the smallest `legal_entity_id`. When a legal entity's members map to several table parents, the smallest is used.
- **Pair log.** `pairs` also holds the automatic V1/V2 merges (anchor = smallest key in the group, status `auto`) and V4 pairs vetoed below 92 (status `vetoed`), so the log explains every link. An extra column `score_detail` keeps the scoring evidence without the outcome sentence, and the `cached_pairs` path reads candidates from rows with `stage == "V4"`. A pending pair whose records end up in one legal entity through other evidence is marked `auto`. `vendor_map` gains an `evidence` column.
- **`vendor_map.stage`.** This is the strongest link a record took part in, ranked V1 > V2 > human > V4. A singleton with a parent-table link gets `V3` at tier A. Identifiers use at least five digits (`LE00001`).
- **Recall risk (measured, then handled).** Truncated legal forms ("... Corpor") and typos inside descriptor tokens ("Fastners") did cost recall on the tuning seeds; both are now handled, see "Accuracy tuning".
## Ingestion and units

- `load_file` keeps only PRD 3.1 columns. Headers are matched through the optional mapping, then by lower-casing and replacing non-alphanumerics with `_`. Fully blank rows are dropped but `source_row` still counts them. The delimiter is the most frequent of `, ; tab |` in the header line. Only the first XLSX sheet is read; legacy `.xls` is refused.
- `lines` carries typed values, not literal text: dates are `datetime64[ns]`, numbers `float64` (`payment_terms_days` is rounded, not nullable-int). Text columns stay stripped strings with `None` for blanks. `currency`, `vendor_country` and `uom` are upper-cased, `spend_type` lower-cased; invalid country, currency or `spend_type` values become blank.
- Number parsing accepts thousands commas, a currency symbol, `(x)` and a trailing minus as negatives; decimal commas are not supported. Dates: ISO (with `-`, `/` or `.`), `YYYYMMDD`, `MM/DD/YYYY` (day first when the first part exceeds 12) and `DD-Mon-YYYY`.
- The 1% rule counts, per file, the rows hit by any of unparseable date, number or currency (one union), and applies the resulting severity to all three findings. FX-missing and blank `vendor_id` each have their own 1% test. "More than 1%" is strict: 1 of 100 is a warning, 2 of 100 blocks.
- Added rules the PRD does not list: blank `vendor_id` (excluded; 1% rule), blank `uom` on an item row (warning, conversion `unconverted`), unusable optional values (`pack_qty`, `payment_terms_days`, `payment_date`, `contract_end_date`: blanked, warning), no lines in the window (blocking), `unit_unconverted`, `not_item_addressable`, `unmapped_category`, `unknown_l2_code`, `outside_window`, `partial_year_scaled`, `no_payment_terms` (lever 3 off), `aggregated_mode`.
- Dollar values in `data_quality.amount` are absolute, annualised, in reporting currency. Window and parse rules cover the whole file; row-level rules cover in-window lines. FX-missing rows have no convertible value, so their amount is 0.
- "Anywhere" rules (`no_contract_end_date`, `no_payment_date`) are reported once with company `both`. `meta.features` holds `contract_phasing` (any contract end date), `payment_terms` (both files have terms or payment dates), `observed_days_to_pay` (any payment date, never in aggregated mode) and `benchmark_line_test`.
- The FX table is read as already expressed in the reporting currency (PRD 3.2); `reporting_currency` is a label, forced to rate 1.0, and a table that lists it at another rate raises `ValueError`.
- Price comparison: `price_comparable` is first set by validation (amount mismatch, non-positive price), then `prepare` also excludes lines with no item (`no_item`) and unconverted units (`unit_unconverted`), as PRD 3.5 and 4.6 require.
- Units: a unit that already names a base unit (`EACH`, `METRE`, `METER`, `KILOGRAM`, `LITRE`, `LITER`, `HOUR`) is `confirmed`. A pack unit in an unmapped category has no known base unit and is `unconverted` even when `pack_qty` is given. `pack_qty` is ignored for non-pack units. Fixed-factor units convert to their own base even when it differs from the category dimension; matching compares base dimensions.
- `flag_unit_errors` takes one row per matched item (`price_a/b` converted, `recorded_a/b`, `status_a/b`), uses recorded prices when either side is `unconverted`, picks the nearest pack factor within 3%, and returns `ratio`, `factor`, `rule`, `flagged`, `message`. `combine_status` gives the worst status of an item's lines.
- Category suggestions use the PRD Jaccard literally. With 10 to 12 keywords per L2 and tokens from up to 20 descriptions, a score of 0.3 needs most keywords to appear, so suggestions will be sparse on real data; the threshold is a parameter.
- Category-map labels match after trimming and case-folding; a duplicated (company, label) keeps the last row.
- `prepare` lives in `tieout/ingest/prepare.py` and is re-exported from `tieout.ingest`. `Prepared` also carries `affected_rows` (company, rule, source_row, line_id) with `rows_for(rule, company)`.
## Item matching

- **Bearings: full designation vs "two agreeing attributes".** PRD I2 names one bearing attribute (the full designation with suffixes), but an I3 automatic match needs two. The parser splits it into `designation` (base number with prefix), `seal` (canonical class: `2RS1`, `2RSH`, `LLU`, `DDU` -> `2RS`; `2Z`, `2ZR` -> `ZZ`; ...), `clearance` and other `suffix` codes. Once both sides have a base designation, a missing seal, clearance or suffix reads as "none", so `6204` vs `6204-2RS` and `6204-2RS C3` vs `6204-2RS` conflict because the full designations differ. Only components stated on both sides count as agreements.
- **Critical vs guard keys.** Each family's critical keys (`CRITICAL_KEYS`) are the PRD I2 attributes, some split into parts: for fasteners, the thread diameter plus `pitch`; for PVF, the pressure class as `class` (`#`, `LB`, `CLASS` -> `CL150`), `psi` (PSI/WOG/CWP), `pn` and `schedule`; for electrical, the current rating also covers wire `gauge` and motor `power` (HP/kW); for PPE, the material is split into `material` and `coating`; for abrasives, "grit or geometry" covers `grit`, `thickness`, wheel `type`, `teeth`, `flutes`, point `angle` and the ISO `insert` code. Guard keys (`kind`, `style`, `pitch`, `alloy`, elbow `angle`, `vtype`, `phase`, `rpm`, `frame`, glove `thickness`, `cut_level`, respirator `rating`, `nrr`, `lens`, abrasive `material`, ...) never count towards the two-attribute rule, but a disagreement on one is still a conflict.
- **Generic tokens.** Each number with a unit is one token (`1/2IN` and `0.5 IN` -> `0.5IN`). A same-unit dimension group is one token (`12X10X8IN`, also from `12INX10INX8IN`); a mixed-unit group (`2IN X 60YD`) splits into separate tokens. Unitless `AxB` groups count as tokens. `VAC`/`VDC` read as `V`. A `#` after a number means pounds in the generic family and a pressure class in PVF. The brand `3M` is not a token.
- **Extra guards beyond the PRD (precision first, PRD 4.1).** For I3 in parser families, a unit stated on both sides with no value in common (`40MM` vs `45MM` anywhere in the text) is a hard veto. For I3 in every family, plain unparsed numbers that differ on both sides (`ISO 46` vs `ISO 68`) block the automatic match, so the pair goes to review only. Neither guard applies to I1, so a parser mistake cannot demote a part-number match.
- **I1 details.** I1 also requires the same L2 (the opening sentence of PRD 4.4). Its `score` is 1.0; the description cosine is kept in `cosine`. Conflicts that demote an I1 match come from the family parser only.
- **MPN-like description tokens.** A token from one description is compared only with the other record's normalised `mpn` column value in the same L2. A hit makes the pair an I3 candidate even below the review cosine: tier C, or tier B if it passes the ordinary I3 automatic rule. Tokens are never compared with each other, because that produces too many false hits on tokens like `NEMA4X`.
- **Scale.** For I3, each L2 keeps the entries at or above the review cosine that rank in the top 25 of their row or column (`TOP_K`). Vetoed I3 pairs stay in `pairs` with status `vetoed` for transparency.
- **Cached pairs.** `pairs` carries extra threshold-free scoring columns (`scored_stage`, `cosine`, `conflict`, `subset_only`, `number_mismatch`, `word_mismatch`, `critical_agreements`, `mpn_token`, `facts`), and `cached_pairs` must contain them. Tiers, statuses and evidence are recomputed from these columns at assembly, so changing `auto_cosine` with cached pairs works. Lowering `review_cosine` below the value used for scoring cannot bring back pairs that were never scored.
- **Decisions.** The latest decision per `pair_id` wins (by `decided_at`, then file order). Approvals are applied after automatic assembly, in `pair_id` order. A blocked approval stays `pending` with "Approval blocked: X is already matched to Y". Rejecting an automatic pair frees both records for their next candidate. An approved pair that the matcher did not propose in this run is added as a `human` row when both records exist.
- **Records.** `build_item_records` uses the lines' `item_key` when that column exists. Otherwise it derives the key: `item_code`, else `MPN:{mpn}|{manufacturer}` with the manufacturer V0-normalised (lower case). A record's L2 is the most frequent one on its lines (ties broken lexically); its family comes from those lines, falling back to the taxonomy.
- **Manufacturer V0.** `normalise_manufacturer` is the vendor module's `normalise_name`: V0 steps 1, 4 and 5 (the dba and branch steps do not apply to manufacturers). The local copy is gone. Two small behaviour changes come with it: a leading "the" is dropped only when more follows, and at least one token is kept (`Ltd` stays `ltd`). `prepare` builds the `MPN:{mpn}|{manufacturer}` item key with the same function, as ARCHITECTURE.md specifies; it used to lower-case only (`acme corp` is now `acme`).
- **I0 details.** An `x` between numbers is joined when it is spaced on both sides or attached on both sides (`NEMA 4X 24` is not joined). `M8-40` becomes `M8X40` only when an integer follows the dash, so the pitch in `M8-1.25X40` is kept. Inch and foot marks become `IN` / `FT`, and units are glued to their numbers.
- **Abbreviation clash.** `abbreviations.csv` expands `SW` to `SWITCH`, but in pipe fittings `SW` means socket weld. The PVF parser therefore reads `SWITCH` as socket weld.
- **pandas 3.** `item_map` and `pairs` use object columns so that blanks stay `None` (pandas 3 would otherwise infer `str` with NaN).
## Synthetic data

- All rates, counts and calibration knobs live in `synthetic/config.py` (`GeneratorConfig`). `scale` multiplies every count and spend figure; tests use `scale=0.15`. One NumPy generator is threaded through; output is byte-identical per seed, whatever `PYTHONHASHSEED` is.
- "Shared items are about 35% of each company's item records" cannot hold for both companies with one-to-one sharing (5,500 against 3,500 records), so 35% applies to all item records together: 1,575 shared items, 29% of the acquirer's records and 45% of the target's.
- "MPN present on 60% of shared items" means both records carry the MPN; a further 25% have it on one side only. Unshared records carry an MPN 45% of the time. A few records (3% acquirer, 7% target) have an MPN but no item code, so their `item_key` is `MPN:{mpn}|{manufacturer}`, the manufacturer part using PRD 4.3 V0 normalisation. `truth_item_map.csv` also carries `item_code`, `mpn` and `manufacturer` so evaluation can re-key if the engine normalises differently.
- `true_gross_gap_usd` = (dearer company's volume-weighted USD price per base unit − cheaper company's) × the dearer company's net base-unit quantity, from the written lines (fixed FX table, returns netted, spot buys excluded). It is PRD 5.2 `G1` with perfect matching, one buying group per company, `a = 1` and no capture probability. Gaps explained by freight terms, and near-identical look-alikes, are recorded as zero. Shared items are bought from one vendor per company, so the company price and the engine's group prices agree up to small site-level noise (1.2%).
- `cause` is one of `price_gap_same_vendor` (same true parent), `price_gap_switch`, `none` (no planted gap; small noise gaps remain), `unit_trap`, `freight_terms`, `near_identical`. `is_distractor` is 1 for any item carrying a distractor (near-identical, freight terms, unit trap, spot buy), named in the extra `distractor_type` column. `truth_distractors.csv` lists every planted distractor with its record keys, and `manifest.json` names the memorable trap and the concentration category.
- Unit traps are shared count items where one side records the price of a pack of N either against `EA` (60%) or against a pack unit with no size anywhere (40%); their planted gap is zero. The memorable trap is a $1.2M jobber drill bit that the target buys per pack of 12, recorded as `PK` with no pack size. Pack differences with no size anywhere (a quarter of the 12%) are not flagged as traps, although bridge step 1 removes them too.
- The 300 near-identical pairs put a one-attribute variant of an acquirer item (a third of them truly shared) into the target, preferring a neighbouring value (M8X40 against M8X45). The 60 similar-vendor pairs are a third each: same stem with disjoint descriptors, a one-letter stem change, and one name a subset of the other. Their tax IDs follow the normal 30% missing rate.
- Concentration: one shared bearings parent holds about 48% of L03.01 (critical, cap 60%), so the cap lets only a small fraction of the remaining spend move.
- Incoterms: both companies standardise on FCA for 90% of vendors, and a shared legal entity keeps its incoterm in both companies 85% of the time, so incoterm mismatches outside the 40 freight distractors stay modest. Currencies are assigned per vendor record (Canadian vendors invoice CAD, European vendors EUR) until the line shares are met; contracts are assigned per vendor until 40% of item spend is covered. The FX rates mirror the shipped illustrative table.
- Descriptions: the acquirer writes adjective-first, space-separated text cut at 50 characters; the target writes head-noun-first, comma-separated text cut at 40, with `"`, `CL150`, `LG` and `2POLE` where the acquirer writes `IN`, `150#`, `SZ L` and `2P`. Generic-family numeric tokens are written identically by both, so they differ only in order, separators, abbreviations and truncation. When a field is full the clerk drops optional words (colour, lining, coating) first; a quarter of the target's long descriptions are simply cut mid-token.
- Calibration on seed 4, using perfect-matching proxies from the generator's own truth: planted gross gap 2.8% of spend, naive proxy 5.5%, lever-1 base proxy 1.6%. The engine will land lower wherever it misses matches; `price_gap_scale`, `gap_median`, `shared_spend_lift` and `unit_trap_count` are the knobs if the PRD 8.3 test fails.
## Lever 1 and bridge

- **Two line sets.** The *defensible* set is the price-comparable lines in base units. The *naive* set adds the unconverted lines, measured in their recorded unit (`quantity_ann`) as "comparing unconverted pack units at their recorded price" asks. Rows excluded under PRD 3.3 (amount mismatch, non-positive price) are in neither set: the naive paragraph says so explicitly, and as the more specific statement it governs the `q[k,g]` formula's "lines with a `confirmed` or `parsed` conversion". So `q[k,g]` is the denominator of `p[k,g]`, and `p × q` is the group's net amount.
- **Which items count.** The naive figure covers *matches* only ("computed on all matches"): tier A/B items plus tier C candidates. Items one company buys are in no figure, even with gaps between its own sites. "Each record using only its single best candidate" is a greedy one-to-one pass over pending or deferred `item_match` pairs between records with no tier A/B partner, by descending score, ties by record key. Such a pair counts under the smaller of its two canonical ids, so scorecard ids always exist in `item_map`.
- **Netting.** A group gets a price only when its net quantity and net amount are both positive. Other groups contribute zero and add nothing to the item's combined quantity. An item whose net quantity over all its groups (active line set) is at or below zero is excluded (PRD 10.1).
- **Step 1** removes three things: items with a suspected unit error that is not cleared, items whose converted lines carry more than one base unit (the PRD 3.5 "base dimensions differ" exclusion, which is a unit problem), and unconverted lines, by switching to the defensible set. The 3.5 flag uses `flag_unit_errors`. Each side's status is the worst status over its naive-set lines, recorded prices come from the naive set and converted prices from the defensible set. `removed_at_step1` lists every item with one of these reasons, even when its naive gap was zero.
- **Negative steps.** Steps 2 to 7 can only remove dollars. Step 1 can add them, because dropping cheap unconverted lines can raise a group's price. As the PRD says, a negative step is shown as zero and carried into the next. When the carry is still negative after step 7 (that is, `F_7 > F_0`), it stays in step 7, so the tie-out always holds. `totals.lever1.bridge` holds the shown steps and `bridge_raw` holds `F_(i-1) - F_i`. `bridge_detail` rows (only non-zero ones) sum to the raw steps.
- **Benchmark.** "Combined annual quantity" is the sum of `q` over priced groups. "Purchase lines" are lines with positive quantity in the active set, and the 10% share is inclusive. Prices tie when they are equal to 9 decimals; the tie-breaks are larger quantity, then the acquirer, then the group key (site, parent) for determinism. The fallback price is each company's net amount over net quantity on its priced groups, with the same tie-breaks. A gap of at most 1e-9 × the reference price is treated as zero.
- **What the holder means for each filter.** Holder, change type and the incoterm test always use the reference price in force: the absolute-minimum group while filter 3 is off, and `p_star` once it is on. This matters only for non-cumulative filter combinations, because the bridge switches filters on in order.
- **Incoterms.** The PRD defines "the benchmark holder" as a company. Each group's dominant incoterm is therefore compared with the holder company's dominant incoterm on the item: by spend, blanks ignored, ties lexical, and a blank on either side means not assessed. An `incoterm` review item is raised for a matched item when a held group would otherwise have a positive gap. Its stake is that `G1`, and approval makes every group of the item comparable. The PRD gives no message wording for incoterms, so the text is ours.
- **Contract share.** `a[k,g]` is the quantity share of the group's comparison lines whose contract ends blank or on or before close date + horizon (`DateOffset` months), clipped to [0, 1] because credits can push it outside. The close date is `assumptions["close_date"]` when present, otherwise the first day after the data window. When no lever-1 line has a contract end date, or no close date is known (aggregated mode without a period), `a = 1` and `totals.checks.contract_lock_in_assessed` is false.
- **Capture probabilities.** Per-category overrides are read from `assumptions["category_settings"]`: a mapping or frame keyed by `l2_code`, with the `category_settings.csv` column names. A blank or missing cell falls back to `assumptions["lever1"]`. Validating the probability triples is the loader's job (PRD 5.1).
- **Internal variance** is the dollars bridge step 4 removes: the gross gap of the holder company's own groups against `p_star`, before incoterm, contract and probability. It is listed per item in `internal_variance`.
- **Upside pending review** is the base net of tier C items with every other filter on. Pending opportunities are listed with status `pending_review`, low/base/high of zero, and their would-be `gross_gap` and `upside_base`.
- **Unit-flag decisions.** Approve without a pack quantity clears the flag. Approve with `pack_qty` converts the item records' unconverted lines (now `confirmed`, price-comparable) and re-runs the 3.5 test. An item that is still flagged then shows as `pending` again, and with both sides confirmed only rule (b) can fire. Reject and defer keep the item out. Review items are raised for matched items only, because tier C pairs are already in the queue. The stake is `G1` with the flag cleared.
- **Opportunity attributes.** `tier` is the item-match tier. `vendor_tier` is the weakest `vendor_map` tier among the vendor records on the contributing groups' lines and the benchmark group's lines (`None` when all are singletons). Tier C vendor links are already separate parents in `vendor_map`. `sites_affected` counts distinct (company, site) among contributing groups.
- **Trace.** A line's contribution to a figure is its group's dollars × the line's quantity share of the group's comparison lines (naive quantity with filter 1 off, base quantity with it on). With filter 6 on, the share is taken over contract-open lines only, since `a` is exactly their share. Credit lines carry negative contributions. `trace.children` runs `total:recurring → lever:1 → lever:1:cat:{l2} → L1:{item}:{change} → grp:{item}|{company}|{site}|{parent} → line_id`, with `item:{id}` nodes under the bridge, internal-variance and upside figures. `trace.figures` maps each dotted money path in `totals` to its node and measure, and `resum` recomputes a figure from its lines. Baseline spend is not a synergy total; it comes from `prepare`'s meta.
- **Totals shape.** `levers.lever1` holds `kind`, `gross_gap` and low/base/high; `recurring` sums the recurring levers present; `lever1` holds the naive figure, the bridge, tier A/B splits, upside and internal variance; `checks` holds non-money flags. Levers 2 and 3 add keys under `levers` without reshaping anything.
- **Performance.** `compute_synergy` on seed 1 (59,902 lines, 866 matched items, 3,820 groups) takes about 0.14 s. On a 60,000-line stress table with 1,500 matched items and 36,000 groups it takes about 0.28 s.
## Pipeline and CLI

- **Cached pair scores live in `Results`.** `Results` gained three frames: `vendor_pairs` and `item_pairs` (the full pair logs of `match_vendors` and `match_items`, which are also their `cached_pairs` input) and `vendor_parents` (the parent table the run used). With them and `lines`, `tieout.pipeline.match_lines(..., vendor_pairs=..., item_pairs=...)` re-runs clustering and one-to-one assembly without rescoring, from a saved `Results` alone. They are Parquet files like every other frame.
- **Inputs.** `PipelineInputs` takes paths or frames. A frame is passed through `load_file` via an in-memory CSV, so both routes give identical lines (nothing is written to disk). `mapping` is either one header-to-field mapping for both files or `{"acquirer": {...}, "target": {...}}`. Without `vendor_parents` an empty table is used; a parent table without a `country` column is accepted (blank country). Without `fx` the shipped illustrative table is used and `meta["inputs"]["fx"]` says so.
- **Default category map.** Without `category_map`, `prepare` runs once unmapped, `suggest_categories` scores the native categories, the suggestions at or above 0.3 become the map, and `prepare` runs again. `meta["category_mapping"]` records the source and the number of mappings. On the generator's data the PRD Jaccard rarely reaches 0.3 (see "Ingestion and units"), so most spend stays unmapped in that mode.
- **Review queue.** `review_queue` holds every vendor and item pair whose status is `pending` or `deferred`, with `label_a`/`label_b` (vendor name or item description), `spend_a`/`spend_b` (annualised in-scope spend of each record) and `dollars_at_stake = spend_a + spend_b`, sorted by dollars at stake (descending), then `pair_id`. `review_log` is the validated decisions log as supplied. Lever 1's `unit_flag` and `incoterm` items join the queue once the synergy stage runs (see "Synergy in the pipeline").
- **Meta.** `meta` extends `Prepared.meta` with `scenario`, `seed`, `view`, `report_date` (`as_of`, else today), `category_mapping`, `inputs`, `thresholds` (the four values used), `stages_run` and `matching`. `matching.vendors` gives the PRD 6.13 staged counts as `records` -> `after_normalisation` (distinct V0 names) -> `legal_entities` -> `parents`; `matching.items` gives `records` (distinct item keys on the lines) -> `matchable_records` (records in a mapped L2) -> `canonical_items`. Both also carry counts by stage and tier and the number pending review.
- **Synergy stage.** Wired in after matching; see "Synergy in the pipeline".
- **CLI.** `python -m tieout run` writes the full `DIR/results/` and prints the staged counts, the naive figure and the defensible range. A blocking validation error prints the report to stdout (blocking findings first, each with its fix, then the other findings) and exits 2, as does an unreadable or oversized file. Exports do not exist yet: unless `--no-exports` is given, one line on stderr says they were skipped.
## Synergy in the pipeline

- **Shape.** `run_pipeline` is load -> prepare -> match -> `recompute`. `recompute(results, assumptions)` runs `tieout.synergy.evaluate` and fills every synergy frame, `totals` and the trace; `apply_decisions(results, decisions)` re-runs `match_lines` on the cached pair logs (no rescoring) and then `recompute`. All three return a new `Results`; nothing is mutated.
- **Assumptions in `recompute`** are merged over the defaults, exactly as `run_pipeline` merges its overrides, so a caller passes an edited copy of `results.assumptions` to keep the run's category settings. The lookup order is defaults, then the `--category-settings` file (stored as `assumptions["category_settings"]`, a mapping `l2_code -> non-blank cells`), then the `--assumptions` overrides.
- **Category settings file.** `read_category_settings` keeps `criticality` as text, reads every other cell as a number in [0, 1], and requires the cells given of each probability triple to be ordered (PRD 5.1: the loader rejects anything else). Blank cells are dropped so they fall back to the global value.
- **Decisions are the whole log.** `apply_decisions` takes the complete decisions log and replaces `review_log` with it, so undo is a log without its last row (`undo_last`). The pair logs it returns become the next cache: the item matcher already re-derives tiers and statuses from the threshold-free scoring columns, and a reviewer-added `human` row is dropped again when its approval is undone. A test checks that a decision applied this way gives the same maps, queue and totals as a full run with that decision, and that undoing it restores the original.
- **The cache.** `Results.synergy_cache` holds `SynergyCache` (buying groups, item facts, spend cube), which depends on the lines, the maps, the pair log and the decisions but not on the assumptions. It is in memory only: not saved, excluded from `==`, cleared whenever matching changes, and rebuilt by the first `recompute` after `Results.load`. On seed 4 that is about 0.2 s of a 0.35 s cold recompute; a warm recompute is about 0.15 s.
- **Tornado and scenarios are not recomputed** with every assumption change: about 60 base-case evaluations plus three scenarios cost about 1 s on seed 4, twice the PRD's half-second budget. They are view functions on the same cache (`Results.cached_synergy()`, see "Result views").
- **Maps carry labels.** `vendor_map` gains `spend` and `item_map` gains `description` and `spend` (from the record builders), so the queue, the masked vendor codes and the review cards need nothing but `Results`.
- **Review queue columns.** `canonical_item_id`, `message`, `ratio`, `factor` and `stake` are added. `stake` is the lever-1 gross gap that approval would add (PRD 6.5 stake line): for a tier C item candidate, the would-be gap of its pending opportunities; for a `unit_flag` or `incoterm` item, the engine's stake with the flag cleared; none for vendor candidates. The queue's sort key stays `dollars_at_stake` (spend of both records). Text columns hold `None` for blanks whichever part a row came from.
- **Switched-off features.** `meta["switched_off"]` maps each feature that is off to the sentence that says what would switch it on (PRD 6.13): contract lock-in, contract-aware phasing, lever 3, observed days-to-pay, the benchmark line test (aggregated data), incoterms, the scorecard and the sensitivity chart. `meta["stages_run"]` now ends with `synergy`.
- **Evaluation artefacts as inputs.** `PipelineInputs.scorecard` / `sensitivity` (CLI `--scorecard`, `--sensitivity`) are JSON files carried on `Results.scorecard` / `Results.sensitivity` unchanged; the engine never computes them (PRD 4.7 isolation).
- **Saving.** Frames are Parquet with zstd compression. The trace is saved as `trace.parquet` (one row per parent -> child edge, in order) and `trace_amounts.parquet` in long form with only the non-zero line amounts; the line and measure orders travel as the categorical categories, so the wide frame comes back exactly. `trace_figures` and the other dictionaries are in `results.json` (numpy scalars written as plain values). pandas 3 reads every text column as its `str` dtype, so `Results.load` turns columns that were saved as `object` back into `object` with `None` blanks, using the pandas metadata in each file.
- **Engine fix: no mapped category.** When no line maps to the taxonomy (for example the CLI's suggested category map on a small file), lever 2 indexed an empty per-category array and raised. `SpendCube.per_line` now looks a per-category value up for each line with a sentinel for unmapped lines; results for mapped lines are unchanged and the run reports zero levers (PRD 10.1).
- **Property test fix.** `test_low_base_high_are_ordered` checked every opportunity, including lever 2, which PRD 5.9 exempts; a random seed found a lever-2 row with base above high. It now checks lever-1 opportunities, the lever-1 total and, as 5.9 requires, total recurring.
- **Timings on seed 4 (laptop).** Full pipeline about 4.5 s; cold recompute about 0.35 s, warm about 0.15 s; a review decision about 1.5 s. The tests assert twice the PRD bounds (60 s, 1 s, 4 s) times `TIEOUT_TIMING_SLACK`.

## Result views

- **Where they live.** `tieout/views/` implements them (`overview`, `charts`, `tables`, `review`, `trace`, with formats, labels and masking in `common`); `tieout/results.py` re-exports every public name, so pages import from `tieout.results` (PRD 9.2). Views are pure: `Results` (+ `view`) in, plain dictionaries and frames out, no Streamlit or Plotly. Every money value is returned as a number beside its display text, with the `figure_id` that `trace_for` opens. `view` defaults to `meta["view"]`.
- **Number formats (PRD 6.11).** Headline ranges use an en dash and one unit, `$8–12M` (nearest $1M once the upper end reaches $10M, else $0.1M, which also applies to small figures, so $25k shows as `$0.0M`); equal ends collapse to one figure; a range with a negative end writes each end in full. Tables round to the nearest thousand as `$184k`. Negative values use the minus sign U+2212, never brackets. Unit prices have four decimals.
- **Headline (PRD 6.4, 7.2).** "{L}–{H} of run-rate savings is defensible; the naive figure of {N} is not." When the naive figure is not above the high case: "The naive figure of {N} holds up: {L}–{H} is defensible". A zero naive figure drops its clause; a zero range gives "None of the naive figure of {N} is defensible." (or "No run-rate saving was found." when both are zero). The texts are well under 120 characters; a cut with an ellipsis guards the limit.
- **Overview.** The three figures are run-rate saving (recurring) and cash release and one-time cost (one-time, `kind` keeps them apart); cash shows lever 3's switched-off message when lever 3 is off. The confidence strip splits the lever-1 base case by item-match tier (lever 2 does not rest on item matches) and shows the lever-1 upside pending review. The cards are the largest lever-1 opportunity by base, the item with the most naive gap removed at bridge step 1 (with its unit-flag message when one is queued, else an unconverted-pack note), and the category with the largest savings forgone.
- **Bridge and waterfall** are stacked bars with an invisible base (`bar_base`, `bar_height`), signed `amount`s and a `level` after each bar; the final bar carries the recurring low and high. `items` counts the items behind a removal step. The waterfall's net-spend range runs from the high case (most saved, least spend) to the low case.
- **Charts.** The Pareto compares vendor records (before matching) with parent vendors (after), giving how many vendors make up 80% of spend. Price dispersion uses the defensible price per buying group and the benchmark. The matrix sizes lever-1 bubbles by their groups' spend, lever 2 by the post-move base `B2` and lever 3 by the vendor's spend, and labels the ten largest. Phasing by quarter puts savings by wave, costs (negative) and lever-3 cash in separate columns; by year it adds a total row whose net equals `phasing.net_three_year`. Concentration keeps the five largest vendors per category and folds the rest into "All other vendors".
- **Tornado and scenarios** are computed when asked for, on `Results.cached_synergy()` (about 1 s together on seed 4), not on every recalculation. The scenario table lists the current assumptions, the three presets and any saved scenarios (complete assumption sets).
- **Review views.** The stake line reads "Approving adds $Xk to the gross gap" for item, unit and incoterm candidates and "Approving links $Xk of annual spend" for vendor candidates. Evidence sentences are split into for and against by their wording (conflicts, differences, vetoes, caps, "review" reasons argue against). Token differences compare the two raw names or descriptions. Progress counts approve and reject as cleared (defer is not) and measures dollars as the spend of both records, like the queue's dollars at stake.
- **Trace panel.** `trace_for(results, figure_id)` takes a dotted `totals` path or any trace node and opens one level: components re-summed from their own rows (largest first, zero rows dropped), and the source rows with a non-zero contribution, as received next to their normalised form. Under total recurring each lever is measured with its own measure (lever 1 base, lever 2 base), so the components add up; phasing nodes and net spend combine totals rather than split one, so they list rows only. `copy_table` is the rows as tab-separated text.
- **Integration-office view (PRD 6.9), implemented once in `common`.** Parent vendors become `Vendor 017`-style codes by descending combined spend (ties by id; the width grows past 999 vendors, so the demo uses four digits). Categories with fewer than three parent vendors with positive spend are labelled "Other" and summed together; unmapped spend is "Unmapped". Opportunities aggregate to lever x category (lever 3 to one "Payment terms" row); the Overview cards and reconciliation name categories, never items. The review queue, price dispersion and source rows return `NOT_IN_VIEW`; the trace stops at category level; vendor-record bars in the Pareto are numbered by rank only. The scorecard stays. A test runs every view and every trace node masked and checks that no vendor name, parent or legal-entity id, item id, long item description or unit price (as text or as a number) appears.
- **Tie-out.** A test checks that every total the views show (headline, Overview figures, bridge, waterfall, confidence strip, phasing, reconciliation, scenario "current" row, savings forgone) equals `totals` to the dollar, in both view modes.

## Test suite runtime

Measured with `pytest -n 2 --durations=40` (two workers, like the CI runner) on a laptop: 72 s wall and 136 CPU-seconds before, 42 s and 80 CPU-seconds after. No test was removed and every Hypothesis test still runs 100 examples.

- **Property tests share their examples.** The 13 property tests over the two synergy strategies spent about 75 CPU-seconds, mostly re-running `compute_synergy` on tables other tests in the same file had also generated. `synergy_fixtures.property_test` now gives every property test of a run one Hypothesis seed (derived from `PYTEST_XDIST_TESTRUNUID`, so all workers agree, and new on every run), and each file's `compute` is memoised by the example's JSON form. Tests over the same strategy draw the same 100 fresh examples per run, so each table is computed once. Each test still checks 100 new random examples per run; what changes is that tests in one file check them on the same tables rather than on different ones.
- **`--dist loadfile`** (in `addopts`) keeps a file on one worker, so the memo is shared. `--dist loadgroup` with `xdist_group` marks was tried first: with pytest 9.2 and pytest-xdist 3.8 the group suffix never reaches the node ids, so groups were split across workers.
- **Shared runs.** The small dataset is run once per worker (`small_results`, session scope) for the pipeline, view and evaluation tests instead of once per module, and seed 4 once per worker (`seed4`) for the gates, design targets, performance bounds and the demo check. With two workers seed 4 may still run twice, once for each worker that draws a seed-4 file.
- **Trace labels are built lazily.** `trace_for` built every label table (categories, vendors, items and a row name for every line) on each call; it now builds each on first use, which also makes the panel faster in the app.

## Accuracy tuning

Errors were diagnosed on the tuning seeds 1-3 only (false positives and false negatives read pair by pair). Seed 4 was read as aggregate metrics only. The generator was not touched. Figures are pairwise precision / recall (PRD 4.7) at the shipped thresholds 92 / 0.80; "1-3" is the mean of seeds 1-3.

| Stage | Vendors 1-3 | Items 1-3 | Vendors seed 4 | Items seed 4 |
|---|---|---|---|---|
| First measurement | 0.970 / 0.867 | 1.000 / 0.551 | 0.964 / 0.879 | 1.000 / 0.535 |
| After cycle 1 (item rendering and the two-sided guard) | 0.970 / 0.867 | 0.977 / 0.809 | | |
| After cycle 2 (vendor rules) | 0.996 / 0.963 | 0.977 / 0.809 | | |
| After cycle 3 (item recall, caps below a tuned threshold) | 0.996 / 0.963 | 0.978 / 0.832 | 0.996 / 0.961 | 0.984 / 0.825 |

**Cycle 1: item descriptions.** Most missed item pairs never reached the review cosine: the target writes `BELT,TIMING,920,14M`, which character n-grams with `char_wb` read as a single word. Fixing that let near-identical distractors through, so a guard came with it.

- **Commas and semicolons are word breaks** (I0). They are replaced after units and dimensions are joined, so nothing is joined across a comma. Mixed numbers written with a space (`1 1/2`) are hyphenated first (`1-1/2`), and the parsers' number pattern no longer accepts a space inside a number: `ELBOW,90,3/4"` is a 90-degree elbow of 3/4 inch, not 90.75 inches.
- **Two-sided differences block automatic I3 matches** (`tieout/match/differences.py`, pair column `word_mismatch`). When each description states something the other does not explain (`HSS TIN` / `HSS BLACK OXIDE`, `NO HOLE` / `5 HOLE`, `CL8` / `CL10`, `100R13` / `100R12`), the pair goes to review. Differences by omission are allowed: a clerk dropping a colour or a coating leaves one side with nothing extra. Rendering rules decide what "explains" a word: equal; for plain words a prefix (`HYD` / `HYDRAULIC`) or an abbreviation keeping the first letter and letter order that drops two letters or has no vowel after the first (`SNDG`, `CRBD`, `DSC`, but not `SOOW` / `SEOOW`); a consonant abbreviation of a run of words (`YZN` / `YELLOW ZINC`). Tokens are read as codes, numbers and words (`6805-2Z` = `6805 2Z`; `CL300` is explained by `300#`; numbers count with multiplicity). A last token that is the start of a token on the other side is a cut field and ignored. Like `number_mismatch`, it never vetoes; it only demotes to review (PRD 4.1).
- **Parser consistency.** Bearings: a one- or two-digit token after a bare designation is the inch bore that a hyphen would attach (`UCF206 31` = `UCF206-31`). Abrasives: the diameter is the named one, else the largest stated size that is not qualified as `DEEP`, `LONG` or `WIDE`, so word order no longer changes it (`111IN 1-1/4IN` vs `1-1/4",111IN`). PPE: `SZ 2XL` is size `2XL`, not 2.

**Cycle 2: vendors.**

- **Different countries are never merged automatically.** A legal entity is registered in one country, so two records in different countries are at most siblings. V2 groups are resolved per country, one record per country is offered against the others as `vendor_sibling`, and V4 pairs across countries become `vendor_sibling` (at or above the automatic threshold) or `vetoed`. The veto is cluster-level, like the tax-ID veto. *This departs from PRD 10.1* ("Same name, different countries: not merged on tax ID; name stages apply"): the name stages still apply, but they propose rather than merge. Without it, vendor precision on seeds 1-3 was 0.979 at every threshold (same-name subsidiaries in different countries merge at V2, which no threshold controls), below the 0.98 target.
- **Legal forms cut short or misspelt** are removed at the end of a name (V0): the start of a long legal form of at least three letters (`incor`, `corporat`, `limi`, `com`) and one typing slip from a legal form of five or more letters (`incorporaetd`, `liimted`). A trailing parenthesis that is never closed is a cut branch note.
- **Names cut at the field length.** A company's names were cut when the longest name length is shared by at least 1% of its names (and at least three); this is a pile-up that uncut names do not show (`tieout/normalise/truncation.py`). For a cut name, a final fragment shorter than three letters or the start of any legal form is dropped (`... INTERNATIONAL A` from `AG`).
- **Generic and descriptor words are read through noise** when scoring: a listed word's start cut short (three letters for generic words, four for descriptors), a consonant abbreviation (`intl`, `brgs`, `fstnrs`) or one typing slip (`saefty`, `bearing` for `bearings`). Generic variants are removed like generic words; descriptor variants are spelt in full before scoring, so `zidala brgs` and `zidala bearings` score 100.
- **Distinctive words may differ only by a typing slip.** An automatic V4 merge also needs every non-generic, non-descriptor word on one side to equal, be one slip from (a doubled, dropped or inserted letter, or two neighbours swapped), or be the cut-off start of a word on the other side. A substituted letter is not a slip: `Gilthali` / `Gilthalt` goes to review.
- **Blocking also uses the consonant skeleton of the first word** (vowels dropped, repeats collapsed: `fittondren` and `fitondren` are both `ftndrn`), so a slip in the first four letters does not hide a pair. Blocking only proposes; every guard still applies.

**Cycle 3: item recall.**

- **Descriptions cut at the field length** (same pile-up rule, per company): the final token of a cut description is left out when attributes are parsed, so `SCH 8` (from `SCH 80`) is a missing attribute, not a conflict. It stays in the text for similarity and the other guards.
- **Manufacturer short forms are compatible for I1** when the first words are equal and each later word of the shorter name is equal to, the start of, or an abbreviation of the word in the same place (`PRESTVA` / `Prestva Bearing Ltd`, `ALESTUV ELEC` / `Alestuv Electric Corp`). This extends PRD 4.4's compatibility rule; the MPN itself must still match exactly.
- **Review-at-most caps hold below the automatic threshold.** The weak-name and one-descriptor caps (91) mean "review at most, never automatic" in PRD 4.3, but the tuning grid starts at 85, where a capped 91 would merge. Pairs under either cap are now never merged automatically, whatever the threshold.
- **Not changed:** the abbreviation dictionary (the generator's habits overlap it by about 80% by design, and a test holds that), and `similarity alone never matches`: generic items with fewer than two numeric attributes (`V-BELT BX 34`, `ROLLER CHAIN #50 DOUBLE 10FT`) still go to review however similar they are. They are most of the remaining item misses.

## Dollar-weighted accuracy and sensitivity

- **Feeding the metrics.** `evaluation.evaluate.dollar_metrics` reads the synergy stage's `item_gross_gaps` (`G1` per matched item, before capture probability) and `removed_at_step1`, and applies the existing pure functions. For the tool it evaluates `Results.cached_synergy()` with the run's assumptions; `SeedTruth` now also carries `truth_savings.csv`.
- **The baseline through lever 1.** PRD 4.7 runs the baseline's matches "through lever 1 with all bridge filters on". The baseline's item pairs are many-to-many, while lever 1 counts each record under one item, so `baseline_item_map` keeps each record's single best pair: pairs greedily by descending score, ties by record ids, the same rule the tool's naive figure uses for tier C candidates. Paired records are tier B; vendors use the baseline's connected-component map, so its chained parents decide the baseline's change types and groups. `compute_synergy` then runs unchanged with every filter on, and the three dollar metrics are scored against that item map (an impure canonical item counts as a wrong match).

## Levers 2–3, risk and phasing

- **Stage shape.** `precompute(...)` builds everything that does not depend on the assumptions (buying groups, item facts, the spend cube). `evaluate(cache, assumptions)` is the recalculation, and `compute_synergy` runs both. `compute_synergy` gains an optional `taxonomy` argument (default: the shipped file). It is used only for each L2's default criticality, because `lines` carries `category_type` but not `criticality`. `recurring_base(cache, assumptions)` computes only the base recurring total, for the tornado. Lever-1 frames, lever-1 opportunity columns, `totals.lever1` and `totals.levers.lever1` are unchanged (checked byte for byte on seed 1). `trace.line_amounts` now covers every line, with lever-1 measures at zero off lever-1 lines, and `total:recurring` lists `lever:1` and `lever:2`.
- **Spend cube.** Every in-scope line, sorted by `line_id`. Unmapped lines count in the baseline but in no lever (PRD 3.4), and that includes lever 3. "Addressable" spend is spend in categories where both companies have positive spend.
- **Settings lookup.** Each per-category value is read from `assumptions["category_settings"]` first (a mapping or frame with the `category_settings.csv` columns), then the global assumption, then the default. Criticality comes from the settings file, then the taxonomy, then `standard`. `d` is 0 when the `category_type` is unknown. The user chooses a preferred vendor with `assumptions["lever2"]["preferred_vendor"] = {l2_code: parent_id}`. A choice with no spend in the category is ignored.
- **Lever 2 qualification and preferred vendor.** "Has spend" and "parent vendor" both mean positive net spend in the category. By default the preferred vendor is the one with the largest combined spend over all its lines. Lever-1 `switch` lines are included here because `P` is "current spend". Ties go to the smaller `parent_id`. A non-preferred vendor whose net eligible spend is not positive moves nothing.
- **Which lines are `switch` lines.** The comparison lines (the trace children) of buying groups in an in-range `L1:{item}:switch` opportunity. Pending (tier C) `switch` opportunities assume no saving, so their lines stay in lever 2.
- **Lever 2 per line.** The preferred vendor's eligible lines have weight 1 and the other vendors' eligible lines have weight `f`. `B2 = Σ weight × (amount − lever-1 saving)`, which is exactly `P_eligible + f × M − L1`. `B2` is 0 when `f = 0` (as the PRD writes it) and never below 0. Every qualifying category is an opportunity, so savings forgone stays visible. Its status is `in_range` (f > 0), `cap_reached` or `nothing_to_move` (M = 0). Opportunity `gross_gap` is `B2 × d` (before capture), and `basis_*` holds `B2` per case.
- **Lever 3 groups.** Only lines of vendor records whose `vendor_map.tier` is A or B count. The parent must have positive spend on such lines from both companies. Spend weights are positive line amounts. Observed days are `payment_date − doc_date`, and coverage is the share of positive spend with both dates. Observed days are never used in aggregated mode. When the 80% test fails and either company has no stated terms, the vendor is excluded with one of two reasons: "neither" (no terms and no dates) or "no stated terms" (some dates, but below 80%). Terms count as different when their spend-weighted `T` values are at least 1 day apart.
- **`S[g]` per line.** `S = (1 − φ)(amount − lever-1 saving) − amount ÷ C[c] × N2[c]`, where `φ = f` on lines that move under lever 2 and 0 otherwise. Reading it term by term:
  - the moved part leaves together with its lever-1 saving, which travels with it;
  - the lever-1 saving on the part that stays is deducted;
  - every line takes its spend share of its category's lever-2 saving. "Pro rata by spend" is read literally, over the whole category.
  
  Spend moved under a lever-1 `switch` is not deducted, because the PRD lists only lever-2 moves. A group's `S` is never below 0. Lever 3 is switched off when either company has neither `payment_terms_days` nor `payment_date` on any line, and `totals.checks.lever3_message` says so. Opportunity `gross_gap` is cash before `π3`, and `basis_*` is `Σ S` over the groups whose days rise.
- **Risk.** `category_risk` is long: one row per (L2, parent vendor), with spend and share before and after consolidation. The category-level columns repeat on each row: effective settings, `C`, `P`, `P_eligible`, `M`, `f`, HHI before and after, savings forgone and the sole-source flags. Shares are computed with negative spend counted as 0. "After" reflects lever-2 moves only (post-move spend before savings), not lever-1 switches. A category is sole-source when only one parent has positive spend after consolidation. A sole-source item is a tier A or B item whose lines in both companies carry a single parent. Savings forgone is the base `N2` at cap 100% minus the base `N2` at the current cap, per category and in total.
- **Months.** Month 1 is the close month. A line's available month is the month of its contract end plus 1, when the end falls between the close date and close + horizon. Otherwise it is 0 (contract expired, blank or beyond the horizon). An opportunity's available month is the maximum over its lines. For lever 1 those are its trace lines, for lever 2 the category's eligible lines, and for lever 3 the lines of the groups whose days rise. A recurring opportunity saves in every month from its start month on, so start month 3 gives one month in quarter 1. Contract-aware phasing needs at least one contract end date and a known close date. Otherwise the global ramp applies and every available month is 0. On demo data many lever-2 opportunities start after month 36, because one late contract anywhere in the category sets the category's available month.
- **One-time costs.** Two kinds of move create switch events:
  - a lever-1 `switch` group moves the spend of its contract-open defensible lines to the benchmark group's parent, or to `(re-tender)` when the benchmark is the company-level fallback;
  - lever 2 moves `f × amount` of each eligible line to the preferred vendor.
  
  There is one event per (company, L2, destination). The $25,000 is shared across an event's moved dollars pro rata. Each opportunity's part is therefore `(25,000 × share + 1% × its moved spend) × its capture probability`, incurred in its own start quarter. Costs falling after quarter 12 are in `one_time.costs` but not in the three-year net.
- **Prioritisation.**
  - Change required: `same_vendor` scores 1 and terms 2. A lever-1 switch scores 3 when the buying company already uses the destination parent anywhere, 4 ("re-tender") when the benchmark is the fallback and there is no destination vendor, and 5 otherwise. Lever 2 scores 3 when every company that moves spend already buys from the preferred vendor, and 5 otherwise.
  - Lever-3 criticality is that of the parent's largest category.
  - Sites: lever 1 uses `sites_affected`, lever 2 the (company, site) pairs on lines with positive weight, and lever 3 those of the groups whose days rise (at least 1).
  - Match confidence: tier A automatic scores 1, tier A with a `human` stage 2 and tier B 5. Tier C (pending) scores 5. A preferred vendor with no cross-company link scores 1.
  - Weights and score tables are fixed constants in `prioritise.py`, because the PRD does not call them assumptions.
- **Totals.**
  - `levers.lever2` and `levers.lever3` (`kind` `one_time_cash`) sit beside lever 1.
  - `recurring` is lever 1 + lever 2, and `defensible_range` holds its low and high.
  - `one_time` holds `cash` and `costs`. `memo.financing_value` is cash × cost of capital.
  - `spend` holds the baseline, addressable spend and net run-rate spend per case. `lever2` holds `B2` and savings forgone.
  - `phasing` holds the method, realised savings by year, net three-year value and the beyond-month-36 list (opportunities with base > 0).
  - `reconciliation` holds both band checks and, when the figure is outside a band, the three largest recurring opportunities. `largest_opportunities` is empty otherwise.
  - Net three-year value subtracts one-time costs from realised savings, as PRD 5.6 defines it. It is the only figure that combines the two, and it never touches the run-rate totals.
- **Trace.** The new chains:
  - lever 2: `lever:2 → L2:{l2} → line_id`;
  - lever 3: `lever:3 → L3:{parent} → vgrp:{company}|{parent} → line_id`;
  - costs: `one_time:costs → event:{company}|{l2}|{destination} → line_id`;
  - `spend:baseline`, `spend:addressable`, `spend:net`, `phasing:realised` and `phasing:net` complete the map.
  
  Every money figure in `totals` has a `trace.figures` entry and re-sums from its lines within $0.01, as tested on generated tables.
- **Tornado and scenarios.** The moves:
  - each probability triple's base goes to its low and to its high value;
  - caps move ±10 points, clipped to [0, 1];
  - the horizon moves ±12 months;
  - other numbers move ±25%. Lead times, `min_lines` and maximum days are rounded to whole numbers, and shares are capped at 1.
  
  Reference bands, the close date and the settings file are not moved. Rows are sorted by the larger absolute effect, ties by path. "Central (defaults)" keeps only the `category_settings` file. "Conservative" and "Stretch" set every global base probability, and every `pi*_base` cell in the settings file, to its low or high value. When the low or high cell is blank, the base cell is cleared so that it falls back to the moved global value.
- **Performance.** `compute_synergy` on seed 1 (59,902 lines) takes about 0.29 s. The tornado (around 60 base-case evaluations on the cache) takes about 0.4 s.

## App foundation (session state, trace panel, page scaffolding)

- **Session state.** `app/components/state.py` is the only module that reads or writes the session's results, assumptions and decisions. `current_results()` caches two stages against version counters:
  - decisions applied (`apply_decisions`, about 1.5 s on the demo);
  - assumptions applied (`recompute`, about 0.2 s).

  A re-run with nothing changed returns the cached object. The demo results are loaded once per server with the synergy cache already built, so the first assumption change re-runs only the arithmetic.
- **Assumptions.** `set_assumptions(overrides)` merges a partial or complete nested dict over the assumptions in force. Invalid values raise `ValueError` and leave the session unchanged. Decisions are applied before assumptions, so an override survives a new decision.
- **Decisions.** Session decisions are appended to the base run's own `review_log`, and the last decision per `pair_id` wins. A new decision on a pair replaces the earlier one and becomes the last, so "undo" removes it.
- **Uploaded data.** `set_uploaded_results` and `reset_to_demo` clear this session's decisions and overrides, because they refer to other records.
- **Scenario name.** The header shows `meta["scenario"]`, with `demo` displayed as "Demo merger".
- **View banner.** A one-line banner under the header names the active view in both modes. In the integration-office view it adds that the mode is not a security control (PRD 6.9).
- **Show working.** The dialog and the inline panel are one component, `render_trace`.
  - Selecting a component opens it one level down, and "Back" returns.
  - A component opens in its parent's measure, so bridge steps and unit traps show the dollars they removed. The exception is the run-rate total, under which each lever uses its own measure.
  - Source rows are capped at 500 in the panel and in the copy block, with the full count shown.
- **Charts.** The chart layout leaves Plotly's drag mode at its default, because with drag disabled Streamlit did not report click selections. Hover text gives exact dollars with a minus sign. Text from views is escaped before it reaches Markdown, so that two `$` signs never start maths.
- **AppTest limits.** After the first run, `AppTest` re-runs the current page script without `main.py`, and it cannot re-run a dialog fragment. The header is therefore tested on its own, and drill-down is tested on the inline trace panel. Chart and table selections are injected through their session-state keys.

## Workbook export

- **Formula chain.** Every saving is a capture probability times a fixed gross amount, so each downstream base is a fixed share of upstream savings. `build_workbook` re-runs the arithmetic once (`_engine`, using the synergy stage's helpers), reads those shares and stores them as values; the formulas multiply them by the live savings.
  - Lever-1 rows are `G1 × π`, with `π` looked up in `Category_Settings`.
  - Lever-2 rows deduct lever-1 savings through `Links`: `IF(f > 0, MAX(post-move spend − deduction, 0), 0) × d × π2`.
  - `Payment_Terms` computes `S = MAX(retained spend − deductions, 0)` and cash `= days gained / 365 × S × π3`.
  - Costs are `(fixed × switch-event share + pct × spend moved) × π`.
- **Extra tab `Links`.** PRD 7.1 lists no tab for the lever-1 and lever-2 savings that carry into the lever-2 and lever-3 bases. `Links` holds them in two tables, one row per (target, source opportunity), with the share as a value.
- **No circular references.** Price, volume and cash savings sit in separate column triples on `Opportunities`, and the two link tables use separate columns. With a single savings column, the `SUMIFS` ranges would include cells that depend on the formula itself, and Excel flags a range-level circular reference even when the criteria exclude those cells. `Summary` sums each lever's columns, so recurring and one-time amounts never share a column.
- **Keys.** `SUMIFS` criteria are row numbers (the `No.` columns), never free-text ids. Excel would read `*`, `?`, `~` or a leading `<`, `>` or `=` in an id as a wildcard or an operator.
- **Category_Settings.** A category without its own override shows a formula linking to the named global assumption (black), so editing the global value recalculates every such category. An override shows as a blue input. Caps are recorded values.
- **Check cell.** The check tests internal consistency only, so it stays OK after any assumption edit. Its formula is `IF(ABS(diff) < 0.5, "OK", diff)`, where `diff` sums the identity differences listed under "Consistency checks" on `Summary`:
  - **Clean:** each lever total on `Summary` against an independent sum over its detail tab:
    - lever 1 against Σ gross × π over in-range lever-1 rows;
    - lever 2 against Σ B2 × d × π2;
    - cash against the `Payment_Terms` total;
    - raw bridge steps 1–6 against `Bridge_Detail`;
    - naive − seven steps against lever 1.
  - **Masked:** `Bridge_By_Category` (naive − all raw steps) against lever 1 on `Opportunities`, plus the bridge residual.
  
  The tool's figures sit beside the live ones in "As exported" columns, with a "Change since export (base)" column. Neither is part of the check.
- **Bridge.**
  - Raw steps 1–6 are `SUMIFS` over `Bridge_Detail`.
  - A carry column reproduces "a negative step is shown as zero and moves to the next step".
  - Step 7 is `naive − Σ shown steps 1–6 − lever-1 base`, as PRD 7.1 specifies, so any remaining carry lands where the engine puts it.
  - Amounts are shown as positive removals.
- **Spend_Cube.** Lines are summed over identical company, site, parent vendor, legal entity, L1, L2, canonical item and base unit, since none of the listed columns identifies a single line. Price is spend ÷ base-unit quantity, and an `Addressable` column feeds the addressable-spend formula. On the demo this gives 22,242 rows instead of 60,012.
- **Masked workbook.** The aggregated tabs hold values taken from the masked view functions (`concentration`, `phasing_by_year`, `phasing_by_quarter`, `opportunity_labels`, `category_labels`). `Summary` and `Bridge` are formulas over those tabs.
  - The workbook is not assumption-live: a merged "Other" row cannot carry one capture probability per category. Only the financing memo and the band checks recalculate, and the README and the Assumptions tab say so.
  - `Opportunities` is grouped by the views' labels: lever × category, with lever 3 as one "Payment terms" row. It also carries the tier A, tier B and pending-upside columns the Summary needs.
  - `Bridge_By_Category` holds raw step amounts; the carry is applied on `Bridge`.
  - `Links` and `Payment_Terms` are omitted because they name items and vendors.
- **A1 label.** "Illustrative — synthetic data" appears when `meta.scenario == "demo"` or a seed is recorded; otherwise A1 reads "Tie-Out".
- **Determinism.** The file's creation time is the report date, so the same results give byte-identical files.
- **LibreOffice.** The recalculation test writes a throwaway profile setting `OOXMLRecalcMode` to 0 (always recalculate) and converts with `soffice --headless --convert-to xlsx`. It is skipped when `soffice` is absent. LibreOffice was not available here, so neither the test nor the setting name has been confirmed.
- **Size and time (demo, 60,012 lines).** The clean workbook is 5.5 MB with 40,763 formulas and builds in about 4 s. The masked workbook is 0.09 MB and builds in about 0.4 s. The test evaluator re-evaluates every clean formula in about 3 s.
